# Goofish signing runtime

Goofish (闲鱼) MTOP requests must be signed by Alibaba's
SecurityGuard native library. ZeroSearch runs that library under
[unidbg](https://github.com/zhkl0228/unidbg) — a JVM Android
emulator — via a small harness (`local.goofish.SgHarness`, sources
vendored under `harness/`), and speaks to it over stdio in a
JSON-lines "serve" protocol.

## How a release install works (zero configuration)

The release packages ship a **payload** next to the server binary:

```
<install dir>/
  zero-search-mcp[.exe]
  goofish-payload/
    jre/                  # pinned Java 8 runtime (Temurin / Zulu)
    harness/
      classes/            # compiled SgHarness
      classes-patched/    # the two patched unidbg classes
      lib/                # the pinned unidbg 0.9.9 jars
    payload.json          # payload manifest + app-package source
```

The one component that cannot be shipped is the Goofish app
package itself (~269 MB, Alibaba-proprietary). On the first
Goofish use — normally in the server's background pre-warm, before
any MTOP request exists — the server assembles the runtime in its
own data directory (`~/.local/share/zero-search-mcp/goofish-runtime/`
on Linux, the platform equivalent elsewhere):

1. download the pinned app package (idlefish **7.28.70**, the
   build the harness emulates) from Tencent's app-store CDN —
   the URL is content-addressed by the package's MD5 and recorded
   in `payload.json` — and verify its SHA-256;
2. extract the SecurityGuard `.so` libraries from the package;
3. generate `serve.sh` / `serve.cmd` pointing the harness at the
   payload's JRE and classes, with the package's SHA-256 baked in
   (the harness re-verifies it at every boot).

The device identity is generated by the server itself (the app's
own UTDID algorithm) and persisted next to the runtime. Nothing is
configured by the user: no JDK, no Maven, no APK hunt, no
environment variables. The harness starts once per server process
and is reused for every call; if the harness process dies, the
signer restarts it (bounded), and the server's process-group /
PDEATHSIG handling still guarantees no orphan harness outlives
the server.

Disk budget: ~150 MB for the installed payload, ~540 MB in the
data directory (the app package plus the emulator's staged copy
of it), plus small working files.

## Building the payload (release time only)

```sh
./build-payload.sh linux-x64     # or win32-x64 / macos-arm64
# → runtime/goofish/payload-dist/<platform>/goofish-payload
```

`build-payload.sh` compiles the harness with a JDK 8 `javac`,
collects the pinned dependency jars (via Maven, a prepared flat
directory, or a Maven local repository), downloads the pinned
JRE archive for the platform, verifies its SHA-256, and writes
`payload.json`. The release workflow runs it for every platform
and packs the result into both the installer ZIP and the .mcpb.
`scripts/pack-mcpb.sh` picks the same directory up for local
packing.

## Legacy path: `bootstrap.sh`

`bootstrap.sh` is the older, manual assembly route: given an APK
you supply, a JDK 8 and Maven, it builds a self-contained
`goofish-runtime/` bundle (runtime included, no payload). It is
kept for development and for deployments that cannot use the
payload flow; the server still discovers bootstrap-assembled
bundles exactly as before. Release installs do not need it.

## Layout of an assembled runtime

```
goofish-runtime/          (in the server's data directory)
  serve.sh / serve.cmd    # entry point the server spawns
  goofish.apk             # the downloaded app package
  libs/                   # SecurityGuard .so files from the package
  rootfs/                 # emulator root filesystem (harness-managed;
                          #   the harness stages the APK into it at boot)
  logs/                   # harness stderr
  provision.json          # provisioning marker (inputs + hashes)
```
## Verifying an assembled bundle

Assembly happens out of band (a user-supplied APK, Maven downloads,
native library extraction), so verify the result before relying on
it — otherwise a partial assembly only surfaces minutes into the
first Goofish call, as a harness boot failure:

```sh
./verify-bundle.sh /path/to/goofish-runtime
```

The checks are static (the harness is not started): `serve.sh`
exists and is executable; `goofish.apk` is a readable zip carrying
the arm64 SecurityGuard libraries; the compiled `SgHarness` class
and the patched classes exist; every jar on `serve.sh`'s classpath
exists under `m2repo/`; `libs/` holds the extracted SecurityGuard
`.so` set; `rootfs/` exists; and a JDK 8 is resolvable the same way
`serve.sh` resolves it. Each check prints `[OK]` or `[FAIL]` with
the offending item named, and the script exits non-zero on any
failure. Boot-level verification is the server's first Goofish
call itself.
